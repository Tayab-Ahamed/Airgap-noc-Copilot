# Model Limitations and Validation Status

**Document scope:** ML fault-class predictor (`models/predictor.pkl`)  
**Last updated:** 2026-07-01  
**Audience:** Technical reviewers, procurement evaluators, and NOC engineering leads

---

## 1. Summary

The classifier in this system is trained and validated **entirely on synthetic telemetry** generated by `ml/synthetic_data.py`. It achieves near-perfect same-seed test metrics (macro-F1 ~1.0) and high but lower cross-seed metrics. Both numbers are expected in this setting for reasons explained below. They do **not** imply the model will perform equivalently on real containerlab-derived or production telemetry without further validation.

---

## 2. Why the Same-Seed Test Score Is Near 1.0 — and Why That Is Expected

### 2a. The generative process is deterministic and separable by construction

`ml/synthetic_data.py` calls `sim/fault_injector.py`'s `apply_scenario()` to build the training labels. The same function both **creates** the telemetry drift and **writes** the label. This means:

- Each fault class has a fixed set of features that drift according to a known formula.
- There is no label noise (a row is labelled `congestion` if and only if the congestion drift was applied to it).
- The signal-to-noise ratio is high: the noise standard deviation is 5% of the base value (`_noisy(rng, base)`) while the drift magnitudes are 5–10× the base value over the ramp period.

Under these conditions, any reasonable classifier — including the NumPy softmax baseline — will learn to near-perfectly separate the classes, because the decision boundary is essentially the mathematical inverse of the drift formula.

**This is the correct behaviour for this phase of development.** The primary engineering value of a separable synthetic dataset is that it verifies the entire pipeline (feature engineering → model → risk scorer → API → frontend) functions end to end before real data is available.

### 2b. The same-seed train/test split shares timing structure

The standard 75/25 stratified split is drawn from a single call to `generate(seed=7)`. Because the fault windows are placed at positions determined by `seed=7`'s RNG, the training and test rows come from the same set of windows — they share the same fault start times, the same noise trajectory, and the same rolling-feature context. The model therefore does not need to generalise across different timing configurations to score well on the test split.

### 2c. Cross-seed evaluation is the more honest metric

The `--eval-seed` option in `ml/train.py` generates a **second, independent** dataset using a different RNG seed. This produces:

- Different fault window start times (the RNG controls `rng.integers` for window scheduling).
- Different per-minute noise realisations (different calls to `rng.normal`).
- The same fault class structure and the same 5% noise level.

The cross-seed metric measures whether the model has learned the **general shape** of each fault class (the drift direction and rate), not the specific noise trajectory from seed 7. It is the appropriate number to report when claiming generalisation across generation runs.

**Typical observed values (actual run, training seed=7, eval seed=42, 480 min each):**

| Metric | Value | Interpretation |
|---|---|---|
| Same-seed CV macro-F1 (5-fold) | 1.000 | Expected; not a measure of real-world generalisation |
| Same-seed test macro-F1 | 1.000 | Expected; shares timing structure with training data |
| Cross-seed macro-F1 (seed=42) | 0.995 | More honest; reflects cross-run generalisation |

**Per-class breakdown on the seed-42 held-out set:**

| Class | Precision | Recall | F1 | Support |
|---|---|---|---|---|
| 0 nominal | 1.000 | 1.000 | 1.000 | 2309 |
| 1 congestion | 1.000 | 0.950 | 0.974 | 20 |
| 2 bgp_instability | 1.000 | 1.000 | 1.000 | 12 |
| 3 mpls_degradation | 1.000 | 1.000 | 1.000 | 20 |
| 4 policy_drift | 1.000 | 1.000 | 1.000 | 39 |

The `congestion` class recall of 0.95 (1 missed sample out of 20) is the only imperfection in the cross-seed evaluation. This is consistent with the congestion scenario having the longest ramp time (120 s) and therefore the most variation in where the rolling-feature window falls across different timing seeds.

## 3. What This Model Is NOT Validated Against

### 3a. Real containerlab telemetry

The system has not been evaluated on telemetry collected from a live `containerlab deploy -t sim/topology.clab.yml` run with real FRR containers. Real telemetry differs from synthetic in several ways:

| Characteristic | Synthetic (current) | Real containerlab |
|---|---|---|
| Noise distribution | Gaussian 5% multiplicative | Mixed: Poisson counter noise, quantisation artefacts, polling jitter |
| Fault onset | Smooth linear ramp per `apply_scenario()` | Potentially step-function (hardware-induced) or more gradual (software-induced) |
| Multi-fault overlap | Never (one scenario active at a time by design) | Possible (a congestion event can trigger BGP instability simultaneously) |
| Label availability | Exact (from `apply_scenario()`) | Approximate (derived from `inject_live()` timestamps; not sample-accurate) |
| Nominal variance | Fixed 5% of base | Depends on traffic load, FRR version, container resource limits |
| Feature stationarity | Guaranteed (same base values every run) | Non-stationary (diurnal patterns, traffic growth, maintenance events) |

### 3b. Production NOC telemetry

The model has not been evaluated on production MPLS/SD-WAN telemetry from a real network. Real production data introduces additional challenges:

- **Unknown base rates:** The fault class prior in production is not 1:1:1:1:1. Nominal (`label=0`) rows may constitute >99% of production data, creating extreme class imbalance not present in the synthetic training set.
- **Concept drift:** Production networks change over time (capacity upgrades, topology changes, new traffic patterns). A model trained once and not retrained will degrade as the network evolves.
- **Unlabelled data:** Unlike the synthetic pipeline, production telemetry has no ground-truth labels unless a fault injection event is manually correlated with specific timestamp ranges.
- **Sensor coverage gaps:** Production telemetry may have missing values for some features (e.g. `rekey_anomaly` requires IKE event syslog parsing, which may not be deployed at all sites).

## 4. What Is Needed Before Claiming Real-World Performance

In priority order:

### Step 1 — Collect real containerlab telemetry (within existing project scope)

Run the live containerlab topology and use `sim/fault_injector.py` to inject faults with `DRY_RUN=0`. Collect telemetry via `telemetry/telegraf.conf` during and between injection events. This produces labelled data where the label is derived from the injection timestamp rather than from the generative formula.

Expected outcome: macro-F1 will drop from the synthetic level. A realistic target for a well-tuned model on containerlab data is 0.75–0.90, depending on how cleanly Telegraf resolves the 1-minute polling intervals against the per-second fault ramp.

### Step 2 — Increase synthetic noise to close the sim-to-real gap

The current 5% noise level underestimates real sensor variance. Increase `_noisy()` to 15–25% and add:

- Occasional missing values (simulate polling gaps).
- Autocorrelated noise (real metrics are not IID per minute).
- Multi-fault overlap scenarios (inject two scenarios simultaneously).

Re-train and report the new cross-seed metric. A maintained high metric under higher noise indicates the model is robust; a large drop indicates the decision boundary is too tight.

### Step 3 — Retrain with class priors matched to real distribution

If nominal rows represent 95%+ of production data, the training set must be adjusted (via oversampling or class-weight tuning) to avoid the model defaulting to predicting `nominal` for all inputs. The softmax baseline already uses `class_weight=True`; the sklearn GradientBoosting path should be updated with explicit `class_weight` settings.

### Step 4 — Periodic retraining and drift monitoring

Once deployed against real telemetry, track the rolling precision/recall per class over a 7-day window. If any class F1 drops below 0.70, trigger a retraining run with the most recent N weeks of labelled data. A suggested retraining schedule for a government NOC: quarterly, or on detection of >15% performance degradation.

## 5. Metrics to Report vs. Metrics to Suppress

| Metric | Report to stakeholders? | Notes |
|---|---|---|
| Same-seed test macro-F1 | With caveat | Always disclose it is same-seed; do not present as real-world accuracy |
| Cross-seed macro-F1 | Yes, as primary metric | More honest; always state the eval seed and dataset length |
| In-distribution CV macro-F1 | Yes, as regularisation check | Useful for detecting overfitting to training data |
| Accuracy | Avoid | Misleading under class imbalance; nominal class dominates |
| AUC-ROC | Supplementary | Useful for binary "fault vs. nominal" but loses per-class resolution |
| Containerlab-derived macro-F1 | Required for production sign-off | Not yet available; see Step 1 above |

## 6. Design Decisions That Prioritise Deployability Over Accuracy Claims

The following deliberate design choices in this repository trade accuracy-claim strength for operational practicality in an air-gapped environment:

1. **Synthetic-only training data:** Chosen because real containerlab telemetry is not available before venue setup. The synthetic generator produces data with the same feature and label structure as real injection, making the pipeline reusable once real data is available without code changes.

2. **Linear ramp in `apply_scenario()`:** The ramp is monotone and additive. Real faults may be step-functions, oscillatory, or follow a different time profile. The linear ramp is the simplest assumption that still exercises the rolling-delta and rolling-slope features in `feature_engineering.py`.

3. **No feature noise beyond 5% Gaussian:** Chosen to keep the baseline interpretable and the pipeline verifiable. Noisier generation requires more training data and more complex models to maintain performance, which is appropriate once real data is available.

4. **One active fault scenario at a time:** Chosen to keep class labels unambiguous. In production, multi-fault events will require either a multi-label classifier or a priority ordering (e.g. the highest-risk predicted class is reported).

5. **No time-series model (LSTM/TCN):** The gradient-boosted tree with rolling features is chosen for its interpretability, low inference latency (<5 ms), and ability to run without GPU at an air-gapped site. A time-series model would likely achieve higher accuracy on real data but requires substantially more deployment complexity.

## 7. Relationship Between Metrics and the Risk Score

The API's risk score (exposed at `GET /api/nodes`) is derived from the classifier's `predict_proba()` output, not directly from macro-F1. Specifically:

```
risk_score = max(predict_proba(X)[fault_classes])  # excludes class 0 (nominal)
```

This means even when the classifier assigns the correct class, the risk score may vary depending on the confidence of the prediction. A macro-F1 of 0.90 does not imply risk scores are well-calibrated. Proper calibration (Platt scaling or isotonic regression) should be applied if risk scores are used for automated alerting thresholds.
